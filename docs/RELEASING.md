# Releases and supply-chain security

How LabLink is built, released and verified, and the rules that keep that
process trustworthy.

## Dependencies

- Rust crates come only from crates.io (`deny.toml`: unknown registries and
  git sources are refused) and are locked by `Cargo.lock`; every build and
  test uses `--locked`.
- CI runs `cargo deny check` (advisories, licenses, bans, sources) and
  `cargo audit --deny warnings` on every change, with pinned tool versions.
  OSV-Scanner over `Cargo.lock` is a useful second opinion before a release.
- `THIRD_PARTY_LICENSES.md` is generated by `scripts/third-party.sh` and must
  match `Cargo.lock` (checked in CI and by `scripts/package.sh`).
- Dependabot proposes Cargo and GitHub Actions updates weekly; updates are
  reviewed like any other change.

## CI

- Workflow permissions default to `contents: read`; only the `provenance`
  job gets `id-token: write` and `attestations: write`. It runs only for
  `v*` tags and executes no repository code: it signs the artifacts the
  `release` job built and uploaded.
- Third-party actions are pinned by commit SHA; `actions/checkout` never
  persists the token. There is no `pull_request_target` workflow and no
  secret is used anywhere, so pull requests from forks cannot reach one.
- Every job has a timeout; superseded pull-request runs are cancelled.
- `secrets` scans the full Git history with gitleaks (`.gitleaks.toml`
  allowlists only the synthetic fixtures of the redaction tests).

## Building a release

`scripts/release.sh` builds the committed `HEAD` only (it refuses a dirty
tree):

1. Exports a clean `git archive` of `HEAD`.
2. Builds in `packaging/build.Dockerfile`: Ubuntu 20.04 pinned by digest
   (glibc 2.31 baseline), `rustup-init` pinned by version and SHA-256, the
   Rust toolchain from `rust-toolchain.toml`.
3. `scripts/package.sh` builds the `.deb` and the tarball with every
   timestamp set to the commit time (`SOURCE_DATE_EPOCH`), records the build
   in `BUILDINFO`, and writes `SHA256SUMS`.
4. `scripts/sbom.sh` adds a CycloneDX SBOM of `Cargo.lock`
   (`lablink-<version>.cdx.json`, deterministic) to `SHA256SUMS`.

Rebuilding the same commit gives byte-identical artifacts; to check:

```bash
scripts/release.sh && cp dist/SHA256SUMS /tmp/a
scripts/release.sh && diff /tmp/a dist/SHA256SUMS   # no output
```

In CI, a `v*` tag also gets a Sigstore build-provenance attestation for the
`.deb`, the tarball and the SBOM (`actions/attest-build-provenance`).

## Publishing

- Publish only what CI built for the tag (the `lablink-dist` artifact of
  that run), not files from a developer machine.
- Create the public repository from a fresh single-branch clone of the
  release branch, never by adding a public remote to a working repository
  with other history.
- Before announcing, enable private vulnerability reporting, secret
  scanning with push protection and Dependabot alerts; set the default
  workflow token to read-only and require approval for workflows from
  outside contributors.
- Protect `main` (no force pushes or deletion, changes through pull
  requests) and require these checks, which run on every pull request:
  `lint`, `test`, `dependencies`, `secrets`, `release`,
  `cleanroom (ubuntu:20.04)`, `cleanroom (ubuntu:22.04)`,
  `cleanroom (ubuntu:24.04)` and `aarch64-check`. Never require
  `provenance`: it runs only for `v*` tags.
- Restrict creating, moving and deleting `v*` tags to administrators: a tag
  is what makes CI sign artifacts.
- Date the CHANGELOG entry in the tagged commit; tag that commit, wait for
  its CI run (including `provenance`), check that the `lablink-dist`
  artifact's `SHA256SUMS` equals a local `scripts/release.sh` build, verify
  the attestations (below), then attach those files to the GitHub release.

## Maintaining the one-command installer

`scripts/install-linux.sh` selects an explicitly published release with its
`RELEASE_VERSION` constant, initially `0.3.1`. It uses the existing release
asset names, `lablink_0.3.1_amd64.deb` and `SHA256SUMS`, without a separate
package host or APT repository. It always downloads the selected release's
manifest; never embed a package checksum in the installer. Explicit tag
selection supports prereleases and does not depend on `/releases/latest`.

After a future release's assets have been published and verified:

1. Update `RELEASE_VERSION` to that version in `scripts/install-linux.sh`.
2. Update versioned manual download examples in `docs/INSTALL.md` and the
   provenance example below to the same release. The public README command
   remains unchanged.
3. Run the installer regression checks:

   ```bash
   python3 scripts/test-install-linux.py
   python3 scripts/check-install-release.py
   for test_base in ubuntu:20.04 ubuntu:22.04 ubuntu:24.04; do
       BASE="$test_base" scripts/test-install-linux-containers.sh
   done
   ```

   The release check accesses GitHub to verify asset availability, download
   URLs, checksums and documentation consistency. The Docker check uses real
   release packages on clean Ubuntu 20.04, 22.04 and 24.04 containers. Failure
   scenarios run in isolation; they must never alter the developer's own
   package installation or LabLink configuration.
4. Publish the installer update to `main` through the normal review process.
   Test the exact README command on a fresh supported Ubuntu installation
   after publication:

   ```bash
   python3 scripts/check-install-release.py --published
   BASE=ubuntu:22.04 scripts/test-install-linux-containers.sh --published
   ```

   A local script test cannot prove that the raw `main` URL serves the
   reviewed script.

Keep the previously selected release while a new tag is being built or its
assets are not yet available. Tagged CI builds and the installer target do
not have to advance in the same commit; this avoids selecting assets before
they have been published.

## Verifying a download

```bash
awk '$2 == "lablink_0.3.1_amd64.deb" || $2 == "./lablink_0.3.1_amd64.deb"' SHA256SUMS > package.sha256
test "$(wc -l < package.sha256)" -eq 1 && sha256sum --check --strict package.sha256
gh attestation verify lablink_0.3.1_amd64.deb --repo yusufdxb/lablink \
    --signer-workflow yusufdxb/lablink/.github/workflows/ci.yml \
    --source-ref refs/tags/v0.3.1 --deny-self-hosted-runners
```

The attestation proves the file was built by this repository's CI workflow
from the tagged commit (`--source-ref` rejects attestations made for any other
ref). `lablink version` prints the version and commit; they
match the tag and `BUILDINFO`. The SBOM inventories Cargo.lock, including optional, development and
platform dependencies that may not ship in the binaries. It is not an exact
binary composition map, and does not inventory SQLite bundled through its
Rust wrapper.

## Before every release

- [ ] `cargo test --workspace --locked`, clippy, fmt (CI green)
- [ ] `cargo deny check`, `cargo audit --deny warnings`, OSV-Scanner
- [ ] gitleaks over the full history
- [ ] `scripts/release.sh` twice, identical `SHA256SUMS`
- [ ] `scripts/cleanroom.sh` on ubuntu:20.04, 22.04 and 24.04 (includes the
      security steps: password isolation, other local user, package
      privileges, hostile import, security stop)
- [ ] CHANGELOG `Security` section lists fixed issues
